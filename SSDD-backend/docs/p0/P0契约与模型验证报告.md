## 3. 已确认的 V2 契约

### 3.1 输入

两个模型一致：

```text
name: input
dtype: float32
layout: NCHW
graph shape: [batch_size, 3, height, width]
service baseline: [1, 3, 256, 1600]
color: RGB
external value range: [0,255]
```

图中可直接追踪到：

```text
input → Div(255) → Sub(mean) → Div(std) → encoder
mean = [0.3452, 0.3452, 0.3452]
std  = [0.2053, 0.2053, 0.2053]
```

Java 端只做 RGB 解码、尺寸处理和 NCHW 排列，不能再执行 `/255`、ImageNet normalize 或上述 mean/std。结构报告保存了 float32 常量的实际值；这里按训练配置的小数展示。

两张图均为 IR 8、opset 17，producer 为 PyTorch 2.7.1，没有外部权重张量，也没有自定义 metadata。后处理参数必须独立随模型版本保存，不能期待从空 metadata 中读取。

源码使用直接拉伸至 1600×256，不使用裁剪、letterbox 或自动训练增强。P0 的 11 张图已经是原生尺寸，没有验证 Java 与 OpenCV 的非原尺寸插值一致性。P4 需补充此项及其他图片格式、EXIF、透明通道处理。

### 3.2 输出及后处理

```text
name: output
dtype: float32
graph shape: [batch_size, 4, height, width]
native image output: [1,4,256,1600]
kind: logits, not probabilities
```

两个输出的直接生产节点均为分割头 Conv，末端没有 sigmoid 或 softmax；实测输出存在负数和大于 1 的值。图外处理顺序固定为：

1. sigmoid 得到四类独立概率，允许类别重叠。
2. 每通道 `prob >= 0.5`。
3. 每通道按 8 邻域分连通域，移除面积 **小于 150** 的区域，等于 150 保留。
4. 对去除小区域后的类别总面积做过滤：小于 **[600,600,900,2000]** 时整类置零，等于阈值保留。
5. 保存四通道无损二值掩码，再做结果统计和可视化。

阈值来自当前源码配置，已确定为兼容基线；没有基于标注数据重新搜索最优阈值。

面积过滤在 256×1600 模型空间执行。后续支持任意原图时，先完成此过滤再最近邻恢复掩码；结果像素数按原图空间统计，区域数量沿用过滤后的模型空间计数，不用缩放后的采样形状重新定义缺陷个数。

通道 0～3 对应 CSV 类别 1～4。中文业务名与配色沿用现有前端：凹坑、边缘裂纹、划痕刮伤、氧化铁皮；模型本身没有内嵌中文标签。`defect_count` 是各类连通区域数之和；`defect_pixels` 是四类并集面积，不能将重叠像素重复相加。

完整结果保存四个二值掩码。`mask_image_url` 只作为 0～4 类别索引预览，重叠处选择最高概率的已保留类别，概率相同则取较小类别索引；overlay 同规则，透明度为 0.45。

### 3.3 动态维度和 TTA

两模型均实际通过 `[1,3,128,128]`、`[2,3,128,128]` 小样例，输出相应 `[B,4,128,128]`；错误的 1 通道输入被拒绝。这证明所测试的 batch 和尺寸可执行，不能扩展成任意高宽都受支持。服务基线固定 256×1600，首版批量图片逐张调用。

导出的图不包含 TTA。训练项目配置启用了 TTA，`TTAWrapper` 是图外的三次模型调用。当前基线明确关闭 TTA；若后续启用，需翻回概率图、取三次 sigmoid 概率均值，再执行同一过滤流程。不能平均 logits 代替概率均值，也不能复用原 TTA 评估值来宣称单次推理质量。

## 4. Java 17 CPU 验证结果

环境：Windows amd64、AMD Ryzen 7 9800X3D、16 个可用逻辑处理器、约 30.57 GiB 可见物理内存；实际测试进程为 Eclipse Adoptium Java **17.0.20.1**。Maven 运行于现有 JDK 25，编译 `release=17`，Surefire 显式 fork Java 17 并断言运行版本。

运行时固定 `com.microsoft.onnxruntime:onnxruntime:1.31.1`，CPU，intra-op=2、inter-op=1，每模型 1 次原生尺寸预热。便携 Java 17 及 Python 工具仅放在后端 `target/`，没有修改系统 JAVA_HOME 或 IDEA JDK 设置。

| 模型 | 有效样例 | 加载 ms | 均值 ms | P50 ms | P95 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| Unet++ ResNet34 V2 | 11/11 | 157.91 | 431.90 | 430.44 | 455.24 |
| Unet DenseNet201 V2 | 11/11 | 282.59 | 306.45 | 297.61 | 342.94 |

耗时只包含 `session.run`，不包含解码、张量构建、输出复制、后处理和文件保存；这是一次小规模、单请求串行样本测量，P95 使用 nearest-rank，不能当作生产负载测试或稳定 FPS 指标。加载时间受缓存影响，也不是冷启动承诺。

所有样例输出 shape 正确且均为有限数；每模型参考图的同 Session 重复运行 logits 最大差值为 0。详细结果见 [java-cpu-validation.json](java-cpu-validation.json)。

独立诊断工程共 **5 个 JUnit 测试通过**：模型运行验证、RGB/NCHW 输入打包、阈值/8 邻域/重叠并集、先小区域后总面积及边界值、非有限输出拒绝。图结构检查和 Python 对照另外执行。

## 7. P0 验收与剩余边界

核心 P0 验收已满足：资产完整、两模型可加载运行、Java 17/CPU 可用、输入/输出/后处理规则有源码与计算图证据、参考样例跨语言对齐、固定推理版本、接口差异清单和复现工具齐备。

以下内容不在本轮结论之内：

- 没有 checkpoint 及清理日志，未做 PyTorch→cleaned ONNX 导出等价验证。
- 没有标注集，未评估准确率、mIoU、Dice 或阈值最优性。
- 未验证 GPU、Linux 原生库、多并发、长时间原生内存稳定性；这些属于后续部署和容量阶段。
- 未完成非原尺寸插值、PNG/BMP、EXIF 方向等 P4 输入处理验收。
- 未实现业务服务、模型热切换、上传校验和用户权限，它们仍按总体计划推进。
