# SSDD 钢铁表面缺陷检测系统：后端技术选型与开发计划

> 编写日期：2026-11-03  
> 文档状态：总体开发方案；P0 模型验证、P1 工程与数据库基础设施已完成，尚未实现业务服务。  
> 用户指定：Java 17、Spring Boot 3.5.16；模型功能仅实现 V2。  
> 推荐架构：Spring Boot 模块化单体 + MySQL + ONNX Runtime Java + 本地文件存储。

## 1. 项目现状与目标

当前工作区已有 Vue 前端、Spring Boot 3.5.16 后端基础工程，以及两个 ONNX 文件。P1 已完成 MySQL/Flyway、Web 契约、分页、OpenAPI 和健康检查；后续优先完成现有页面需要的业务，并保持前端已经使用的接口路径和响应结构。

本方案基于以下本地文件，而非仅依据通用检测平台模板：

- `SSDD-frontend/API.md`：认证、检测、模型管理、管理员、操作日志和健康检查约定。
- `SSDD-frontend/src/api/`、`src/types/`：前端实际发送的请求与读取的字段。
- `SSDD-frontend/src/constants/defects.ts`：四类缺陷及前端配色。
- `SSDD-frontend/src/api/index.ts`：Bearer Token、自动刷新和错误处理。
- `SSDD-frontend/vite.config.ts`：`/api`、`/uploads` 均代理到 `localhost:3000`。
- `SSDD-backend/models/Unet_densenet201_v2_cleaned.onnx`：约 110.06 MiB。
- `SSDD-backend/models/UnetPlusPlus_resnet34_v2_cleaned.onnx`：约 98.92 MiB。
- `SSDD-backend/test-images/`：11 张 1600×256 JPEG；目录迁移前后的 13 个文件哈希一致。

P0 已解析计算图，并在 Java 17、ONNX Runtime 1.31.1、CPU 环境运行两个模型的全部 22 个图片组合。输入归一化、输出 logits 和后处理规则已与用户提供的训练源码核对；每个模型的一张参考图还完成 Java/Python 数值与掩码对齐。详见 [P0 验证报告](../SSDD-backend/docs/p0/P0契约与模型验证报告.md)。尚未进行标注集精度评估。

首版目标：注册登录 → 管理员导入并激活 V2 模型 → 质检员上传图片 → 获得分割结果 → 查询、导出历史记录 → 管理员查看用户、统计和日志。

首版按单机、单后端实例、低并发管理系统规划。视频流、工业相机接入、在线训练、模型自动评估、多租户和多实例推理调度暂不纳入范围。

## 2. 技术选型

| 层次 | 选型及版本策略 | 用途与选择理由 |
| --- | --- | --- |
| 开发语言 | **Java 17** | 编译与运行基线均为 17，Maven 设置 `release=17` |
| 应用框架 | **Spring Boot 3.5.16** | 按用户要求固定版本，使用其 parent/BOM 管理常用依赖 |
| Web | Spring MVC + 内嵌 Tomcat | REST、Multipart 上传、CSV 下载，适合现有同步接口 |
| 构建 | Maven 3.9.x + Maven Wrapper | 提交 `mvnw`、`mvnw.cmd`，统一构建入口 |
| 数据库 | 推荐 MySQL 8.4 系列；本机 P1 实测 8.0.34，InnoDB、utf8mb4 | 已在现有 8.0.34 创建独立 ssdd 并验收；8.4 容器路径待环境验证，未自动升级本机服务 |
| 数据访问 | MyBatis-Plus **3.5.18** + Mapper XML | 单表 CRUD、分页和可控的关联查询；使用 `mybatis-plus-spring-boot3-starter` |
| 数据库迁移 | Flyway | SQL 版本化；依赖包含 `flyway-core` 和 `flyway-mysql`，版本随 Boot 管理 |
| 身份认证 | Spring Security + OAuth2 Resource Server/JOSE | JWT 校验使用框架能力；账号登录、签发和刷新逻辑由应用实现 |
| 密码存储 | Spring Security PasswordEncoder，BCrypt | 只存密码哈希；设置工作因子并在开发环境测量耗时 |
| 会话持久化 | MySQL 会话表 | 保存刷新令牌哈希和撤销状态；首版无需 Redis 即可支持登出和权限实时生效 |
| 参数校验 | Jakarta Validation | DTO 校验、分页范围、文件数量和业务参数约束 |
| 模型推理 | ONNX Runtime Java **1.31.1**，CPU 优先 | 两个现有 V2 模型已通过 Java 17 CPU 验证；业务工程在引入时复用此版本 |
| 图像处理 | Java ImageIO、BufferedImage + 数组运算 | 完成基础解码、缩放、掩码和叠加；不支持的解码格式通过专项验证后增加插件 |
| 文件存储 | 本地磁盘 + `StorageService` 抽象 | 首版部署简单；数据目录独立于源码和 JAR，后续可替换对象存储 |
| CSV 导出 | Apache Commons CSV | 处理引号、分隔符、换行及中文编码；具体版本在工程初始化时固定 |
| API 文档 | springdoc-openapi **2.8.17** | 已通过 Boot 3.5.16 启动及文档生成；prod 默认关闭 |
| 日志与监控 | SLF4J + Logback + Actuator | 请求关联 ID、运行日志、健康检查；版本随 Boot 管理 |
| 测试 | JUnit Jupiter、Spring Boot Test、Spring Security Test、Testcontainers MySQL | 认证、权限、真实 MySQL 查询及迁移；主要测试依赖版本随 Boot 管理 |
| 部署 | 可执行 JAR；交付时提供容器部署配置 | 开发期支持 Windows；容器部署单独验证 Linux 原生推理库 |

版本原则：Boot 管理的 Spring、Jackson、数据库驱动等不自行拼版本；非 BOM 管理依赖在首次引入时固定明确版本，不在 `pom.xml` 中使用 `LATEST`、`+` 或版本区间。以上尚未固定的版本是开发前验证项，不表示已完成兼容测试。

MyBatis-Plus 分页所需的 JSqlParser 模块与主库保持同版，按官方安装说明显式引入；不重复引入独立的 MyBatis starter。Spring Boot 3 使用 `jakarta.*` API。[1][2]

ONNX Runtime 的 Java 绑定支持通过 Maven 引入 CPU 或 GPU 运行时。首版使用 CPU 依赖；GPU 作为测量后再决定的优化项，需重新核对操作系统、CUDA/cuDNN 和运行时版本，不同时混装两套原生依赖。[3]

### 2.1 首版架构边界

首版不引入 Redis、消息队列、微服务注册中心或网关。数据库承担会话校验和业务持久化；推理通过受控并发执行。后续只有在实测出现瓶颈或需要异步任务时，再引入相应基础设施。

Java 直接推理可减少一次跨服务调用和一套 Python 部署环境。若 V2 模型依赖当前 Java 运行时不支持的算子，或预处理必须复用复杂 Python 代码，再通过 `InferenceEngine` 接口替换实现；当前计划不预建 Python 服务。

## 3. 工程结构与模块划分

建议在工作区新增独立工程 `SSDD-backend/`，先使用单个 Maven 模块，按业务包分组。

```text
SSDD/
├─ SSDD-frontend/                 # 现有前端
├─ SSDD-backend/
│  ├─ models/                     # 现有模型原件，导入时复制，不覆盖
│  ├─ test-images/                # 11 张验证样例
│  ├─ pom.xml
│  ├─ mvnw / mvnw.cmd
│  ├─ src/main/java/<basePackage>/
│  │  ├─ common/                 # 响应、分页、异常、请求 ID
│  │  ├─ config/                 # 安全、跨域、存储、线程池
│  │  ├─ auth/                   # 注册、登录、令牌、个人资料
│  │  ├─ user/                   # 用户及角色管理
│  │  ├─ model/                  # V2 模型导入、校验、激活
│  │  ├─ inference/              # V2 预处理、推理、后处理
│  │  ├─ detection/              # 单张、批量、记录及统计
│  │  ├─ storage/                # 文件存储、授权访问、清理
│  │  └─ audit/                  # 审计记录和导出
│  ├─ src/main/resources/
│  │  ├─ application.yml
│  │  ├─ application-dev.yml
│  │  ├─ application-prod.yml
│  │  ├─ db/migration/
│  │  └─ mapper/
│  └─ src/test/
└─ docs/
```

业务模块内部采用 Controller → Service → Mapper。Controller 只处理协议与校验；Service 承担权限、事务和业务规则；Mapper 负责 SQL；推理和文件操作通过独立接口调用。DTO、VO 与数据库实体分开，避免直接序列化实体泄露内部字段。

基础包名待初始化工程时确定，不影响本方案。配置通过环境变量注入，密码、签名密钥和数据目录不写入源码。开发端口默认 **3000**，兼容当前前端请求地址。

## 4. 前端兼容与接口范围

### 4.1 通用契约

- 普通业务响应保持 `{success, data?, message?, error?}`。
- 分页保持 `{items, total, page, pageSize, totalPages}`；页码从 1 开始，`pageSize` 为 1～100。
- 分页容器保留 `pageSize`，不能简单地全局启用 snake_case；现有用户、模型、检测字段按 VO 显式映射。
- ID 采用 UUID 字符串，与前端现有类型一致；数据库初版用 `CHAR(36)`，不暴露 Java Long 精度问题。
- 时间统一按 UTC 保存和输出 ISO 8601，界面按本地时区展示；`expires_at` 保持 Unix 秒。
- 失败使用对应 HTTP 状态码及统一错误结构；额外约定 409 冲突、413 请求体过大、429 请求频率或并发超限、504 推理超时。
- CSV、图片及 `/health` 保持各自协议，不套普通业务 JSON 包装。
- CORS 仅放行配置中的前端来源、请求方法和必要请求头；Bearer 认证首版不启用跨域 Cookie。

### 4.2 实现清单

| 模块 | 接口 | 主要行为 |
| --- | --- | --- |
| 认证 | `POST /api/auth/register`、`POST /api/auth/login` | 创建质检员账号，校验密码，签发会话 |
| 会话 | `POST /api/auth/refresh`、`POST /api/auth/logout`、`GET /api/auth/me` | 刷新轮换、撤销会话、恢复用户状态 |
| 个人资料 | `PUT /api/auth/password`、`PUT /api/auth/profile`、`POST /api/auth/avatar` | 密码、昵称、头像 |
| 检测 | `POST /api/detect`、`POST /api/detect/batch` | 调用当前激活的 V2 模型并保存结果 |
| 检测记录 | `GET /api/detect/records`、`GET /api/detect/records/{id}`、`GET /api/detect/records/export` | 查询与导出，管理员看全部、质检员看本人 |
| 模型 | `GET /api/models`、`POST /api/models`、`PUT /api/models/{id}` | 查看、上传和编辑 V2 模型元信息 |
| 模型状态 | `PUT /api/models/{id}/activate`、`DELETE /api/models/{id}` | 预热后激活、移除未使用模型 |
| 管理员 | `GET /api/admin/users`、`GET /api/admin/users/{id}`、`PUT /api/admin/users/{id}/role` | 用户查询和角色调整 |
| 统计 | `GET /api/admin/stats` | 总量、激活模型数、最近最多 100 条成功检测的均值 |
| 日志 | `GET /api/logs`、`GET /api/logs/export` | 按权限查询、筛选和导出 |
| 运行与资源 | `GET /health`、`GET /uploads/**` | 健康响应及受控图片访问 |

历史列表中的 `id` 和类型继承要求的 `record_id` 均返回同一检测记录 UUID。`models`、`profiles` 等关联子对象按现有前端类型返回，不直接暴露 Mapper 查询实体。

用户主键与资料主键继续分开：`users.id` 对应 `user.id` 和 `user_id`，`user_profiles.id` 对应管理员用户详情及角色接口中的 `{id}`。这可避免前端现有两种 ID 含义被混用。

### 4.3 已发现的契约差异及处理决定

| 现状 | 后端方案及配合调整 |
| --- | --- |
| API.md 仍包含 Supabase 认证、自动验证邮件说明 | 首版采用本地账号体系，注册后可登录；同步修订 API.md 的说明和提示。邮箱验证不作为首版前置条件 |
| 用户已限定仅支持 V2，但旧接口文档含其他架构内容 | 对外统一 `arch_version="v2"`、`num_classes=4`；省略架构参数时仍按 V2 校验，明确传入其他值则拒绝。删除过时文档分支 |
| 上传示例的通道数与 V2 描述不一致 | 以实际模型校验结果为准；不兼容四通道输出的模型不可激活 |
| 前端类型未声明 `arch_version`，上传也不传该字段 | 后端返回固定 V2 元信息；前端可补充只读类型和说明，无需增加架构选择控件 |
| API.md 配色与前端常量不一致 | 可视化采用前端常量的颜色，详见第 6 节 |
| 模型类型含 `file_path`，文档示例使用绝对磁盘路径 | 响应只返回逻辑存储键或脱敏相对路径；实际磁盘路径仅在服务端保存 |
| 模型编辑表单允许修改 `file_size` | 文件大小由服务端测量，暂兼容接收旧字段但不以其覆盖真实值；前端改为只读 |
| 质量指标可人工填写 | 保留为空或管理员录入值，记录来源；不将其描述成系统自动评估结果 |
| 首页通过 `all=true` 拉取数据绘图 | 保留最多 10000 条的兼容接口；超限明确给出截断提示信息，后续再增加聚合接口并调整首页 |

首版保留注册密码至少 6 位的现有前端约束，同时限制密码 UTF-8 字节长度不超过 BCrypt 支持的上限，并同步前后端校验。正式部署前若提高复杂度与长度要求，应一起调整界面和 API 文档。

## 5. 数据模型与权限方案

### 5.1 核心表

| 表 | 关键字段与约束 |
| --- | --- |
| `users` | `id`、规范化邮箱唯一索引、`password_hash`、账号状态、时间；注册并发冲突由唯一约束兜底 |
| `user_profiles` | `id`、`user_id` 唯一外键、`role`、`display_name`、头像存储键；角色仅 admin/inspector |
| `auth_sessions` | 稳定会话 `id`、`user_id`、有效期、撤销时间；access JWT 通过 sid 关联 |
| `auth_refresh_tokens` | `session_id`、唯一刷新令牌哈希、消费/撤销时间、替代令牌链；保留轮换历史，不存令牌明文 |
| `model_versions` | UUID、名称/版本、文件存储键、SHA-256、真实字节数、V2 推理配置、指标及来源、上传者、软删除标记 |
| `model_runtime_state` | 固定单行主键、`active_model_id`、状态版本；唯一活动指针，查询时派生模型 active/inactive |
| `detection_batches` | 批次 UUID、用户、模型与配置快照、请求幂等键、执行状态 |
| `detection_records` | 用户、模型、批次、请求幂等键、结果文件键、宽高、像素统计、推理耗时、模型名称/版本快照、时间 |
| `detection_class_stats` | `record_id`、类别索引、区域数、像素数；每条记录四行，联合唯一，便于统计 |
| `operation_logs` | 操作者、事件类型、目标、结果、脱敏详情 JSON、请求 ID、IP、User-Agent、时间 |

模型推理配置保存输入尺寸/布局、颜色顺序、归一化、输出含义、逐类阈值、缩放与后处理规则，并随检测记录保留版本或快照。修改模型名称、删除模型都不能改变历史结果的解释。

主要索引：检测记录 `(user_id, created_at, id)`、`(created_at, id)`、`model_id`；日志 `(user_id, created_at, id)`、`(action, created_at, id)`；会话令牌哈希唯一索引及有效期索引。列表统一按时间、ID 倒序，避免同时间记录分页顺序不稳定。

所有建表与数据升级由 Flyway SQL 管理。管理员通过显式初始化命令或环境配置创建，不提供硬编码管理员密码；初始化动作幂等，已有账号不被启动过程覆盖。

### 5.2 登录与授权

1. 公开注册只能创建 inspector，服务端忽略或拒绝客户端提交的角色字段。
2. 登录签发短期 JWT access token（建议 15 分钟）及高熵随机 refresh token（建议 7 天），维持现有 `user + session` 响应。
3. JWT 包含用户、会话 ID 和必要校验信息；校验签名、有效期、issuer、audience。签名密钥从外部配置加载。
4. 刷新时事务锁定会话，轮换刷新令牌，旧令牌作废；检测到旧令牌重复使用时撤销所属会话链。并发刷新行为需覆盖测试。
5. 受保护请求检查当前会话、账号及数据库中的角色；首版接受这次数据库读取，保证登出与角色调整及时生效。
6. 登出撤销当前会话；修改密码撤销该用户全部会话，要求重新登录。
7. 角色检查与记录所有权检查都在后端实现。质检员不能通过拼接记录 ID、用户参数或文件路径读取其他用户数据。
8. 管理员不能调整自己的角色；敏感变更串行检查，避免并发操作使系统失去有效管理员。

登录、注册和刷新接口增加可配置的频率限制，首版可用有界内存计数实现；多实例部署前再迁移至共享限流实现。

## 6. V2 推理方案

### 6.1 必须先核实的模型契约

只实现 V2 四通道多标签语义分割。P0 已确认两个文件输入为 `input: float32 [B,3,H,W]`，输出为 `output: float32 [B,4,H,W]` logits，服务基线使用 H=256、W=1600。声明动态维度不等于支持任意尺寸。

| 核实项 | 要求 |
| --- | --- |
| 输入 | 节点名、数据类型、NCHW/NHWC、批次维、固定或动态尺寸 |
| 预处理 | 已确认 RGB、NCHW、float32 [0,255]，必要时拉伸至 1600×256；模型已内置 `/255` 和 mean/std，Java 不重复归一化；非原尺寸插值及 EXIF 在 P4 补充验证 |
| 输出 | 已确认 logits，通道 0～3 对应 CSV 类别 1～4；图内无末端 sigmoid，图外执行一次 sigmoid |
| 阈值 | 已从源码配置确认逐类 0.5、比较符 `>=`；先去除小于 150 像素的连通域，再按 600/600/900/2000 过滤类别总面积；不宣称这些值在当前权重上是最优值 |
| 样例 | 至少有代表性输入及参考输出，比较 mask、像素数和类别顺序 |
| 支持性 | 两个现有文件都能在目标 Windows/Java 17/CPU 环境加载并运行 |

模型源码位于用户指定的 `D:/DeepLearning/severstal-steel-defect-detection`，来源文件哈希已留档。当前仍没有标注掩码、训练 checkpoint 或 cleaned 导出前后的权重对应证据，不能作精度和 PyTorch 导出等价结论。源配置启用 TTA，但本次运行与后端首版基线是单次推理；需要 TTA 时必须在图外执行翻转、概率反向还原和均值融合，单独测量。

### 6.2 处理流程与统计口径

```text
图片上传与验证
  → 获取本次请求的激活模型及配置快照
  → RGB 解码、必要时拉伸到 1600×256、构建 [0,255] NCHW 张量
  → ONNX Runtime 推理
  → sigmoid、逐通道 >=0.5 阈值化
  → 在模型尺寸上按 150 像素连通域及类别最小总面积过滤
  → 还原到原图坐标，生成四个二值掩码
  → 每类连通区域计数、像素统计、生成可视化
  → 保存文件及检测记录
  → 返回兼容前端的数据
```

类别固定：1 凹坑 Pit、2 边缘裂纹 EdgeCrack、3 划痕刮伤 Scratch、4 氧化铁皮 IronOxideScale。通道 0～3 必须显式映射到类别 1～4。

- 区域数量：分别对四类掩码做 8 邻域连通分量计数，`defect_count` 为四类区域数之和；这是语义分割区域统计，不承诺等于物理缺陷实例数。
- `class_distribution`：各类掩码像素数；缺失类别显式返回 0。
- `defect_pixels`：四类掩码并集的像素数；`defect_ratio = defect_pixels / total_pixels`，范围为 0～1。
- 多标签允许重叠，因此四类像素数之和可能大于 `defect_pixels`，不得把求和结果当作占比的分子。
- 像素统计、输出掩码和叠加图均采用原图坐标；对离散掩码使用最近邻恢复，填充区域须移除。
- 小区域过滤采用源码的 150 像素及 600/600/900/2000 类别面积规则，在 256×1600 模型坐标执行后再恢复原图；参数和作用顺序随模型配置留档。原尺寸与模型尺寸不同时，区域数沿用过滤后的模型空间计数，像素数和比例按返回的原图空间掩码计算，避免恢复采样重新定义缺陷数量。
- `inference_time_ms` 仅计模型执行耗时，端到端耗时另记日志；不将单张耗时直接标为经过基准测试的 FPS。

配色与前端保持一致：`#ef4444`、`#10b981`、`#3b82f6`、`#f59e0b`。叠加透明度作为配置保存。

V2 的多标签结果不能完整保存在单张类别索引灰度图里。因此，内部保存四张无损二值掩码作为真实结果；为兼容现有 `mask_image_url`，另生成类别索引 0～4 的预览图。重叠区域按通过阈值的类别中最高概率选色，相同概率时按类别索引排序。预览与 overlay 使用同一规则，统计始终来自四通道掩码，界面需说明预览会压缩重叠信息。

### 6.3 会话管理与激活一致性

- 共享 `OrtEnvironment`；复用已加载的 `OrtSession`，不逐请求重新加载百兆模型。
- 对输入张量、推理结果等原生资源及时关闭；Session 在不再被请求使用后关闭。[3]
- 激活流程：串行化管理变更 → 校验文件及配置 → 创建候选 Session → 样例预热 → 切换数据库活动指针与内存句柄 → 返回成功。
- 应用运行时的激活与模型快照获取使用同一协调机制；候选加载失败继续使用旧模型，数据库提交失败关闭候选并保持旧指针。
- 进程异常退出后，以数据库活动指针恢复模型；恢复失败时报告推理未就绪，检测返回 503，不能伪造成功。
- 已开始的检测持有原模型句柄和版本快照；切换后新请求使用新模型。旧句柄等正在执行的请求结束后再释放。
- 批量请求全程使用同一模型快照；不得处理中途混入新激活模型。
- 活动模型禁止删除；存在历史引用时采用软删除和快照保留，物理文件在无运行引用后异步清理。

### 6.4 并发、超时与批量策略

首版同步接口，单次最多 20 张，每张最多 10 MiB；批次内部默认逐张执行以限制内存。模型执行采用有界并发控制，初始并发 1，测量后再调；不使用无界任务队列。

前端单张超时 30 秒、批量 120 秒、模型上传 300 秒。后端设置对应的请求处理预算和入口限流，预算需依据真实 CPU 基准修订。HTTP 超时或浏览器取消不等同于原生推理已停止，资源槽位必须等待实际计算结束再释放。

为保持当前批量成功响应结构，首版采用“整批发布结果”：先验证全部文件，处理中间产物暂存；全部成功后在短事务中发布所有记录。任一失败返回整批错误且不发布部分记录，并清理暂存文件。该策略会浪费失败前已完成的计算，首版接受此取舍。

单张和批量引入可选 `Idempotency-Key` 请求头，按用户及请求内容摘要约束；前端后续补充稳定重试键。服务端生成的 requestId 仅用于追踪，不能替代客户端重试幂等键。若实测 20 张无法满足 120 秒交互预算，再单独设计异步任务接口及前端轮询，不悄然改变现有同步语义。

## 7. 存储、导出和运行保障

### 7.1 文件与数据库一致性

- 数据目录由 `SSDD_DATA_DIR` 指定；分为 models、originals、masks、overlays、avatars、tmp，不直接映射整个目录为静态资源。
- 文件使用服务端 UUID 命名，原文件名仅作展示；规范化并校验路径始终位于数据根目录内。
- 上传先写临时文件，检查真实格式、大小、尺寸及像素上限后处理；模型上传上限 500 MiB，超限在推理加载前拒绝。
- 头像上限 2 MiB；支持 JPEG/PNG/WebP/GIF 的实际解码能力需要逐项验证，统一生成静态头像，限制解码帧数和像素数。
- 使用 Multipart 磁盘暂存，避免将 500 MiB 模型整体读入 Java 堆；请求体总上限同时考虑批量图片和 multipart 开销。
- 文件先写入最终 UUID 位置，再在短事务中发布数据库引用；数据库失败则补偿删除文件。推理和文件 IO 不放在长数据库事务里。
- 定期清理过期临时文件及无引用产物，清理操作只作用于受管目录。旧头像在资料更新提交成功后再清理。
- 数据库备份与文件目录备份配套，交付时验证恢复流程。

### 7.2 图片访问与下载

头像可公开访问。检测原图、掩码和叠加图属于用户数据，查询记录时先检查权限，再生成短期签名相对 URL，例如 `/uploads/results/{key}?expires=...&signature=...`。签名绑定资源键与有效期；文件控制器验证签名及存储映射后返回资源。

该方式兼容前端 `<img>` 无法自动携带 Bearer 头的现状；数据库只保存稳定存储键，不保存会过期的 URL。默认有效期建议 15 分钟，页面长时间停留时需重新获取详情。签名 URL 在有效期内具有访问能力，日志不得记录完整签名参数；模型文件不提供公开下载路由。

### 7.3 导出与日志

- 检测记录和操作日志均支持 CSV；权限过滤复用列表查询条件，防止导出绕过数据范围。
- 单次最多 10000 行，使用分批读取和流式写出；中文 UTF-8，可加 BOM 兼容常见表格软件。
- 转义 CSV 分隔符、引号、换行；对以 `=`、`+`、`-`、`@` 等开头的用户文本防止公式注入。
- 成功业务的审计在事务提交后写入；失败事件用独立机制记录，避免业务回滚把失败审计一同清除。
- 操作日志禁止记录密码、令牌、签名 URL 和整张图片。必要的敏感管理操作将审计写入与业务变更放在同一事务以保证可追溯。
- `/health` 维持前端文档要求的基础存活结构；模型就绪与数据库状态通过受限 readiness/Actuator 端点表达，无活动模型不影响账号管理页面启动。
- 日志记录 requestId、接口、用户 ID、耗时、错误分类；对外不输出堆栈、绝对路径或 SQL。
